# Seat Layout — Ist-Architektur

Stand: 2026-09-09, vor Implementierung dieser Aufgabe. Pfade mit `src/` beziehen sich auf Checkpoint; Backend-Pfade beginnen mit `services/seat/`. Befunde stammen aus statischer Codeanalyse; eine erfolgreiche Browser-Reproduktion wird damit nicht behauptet.

Next.js 16.2.3, React 19.2.4, MUI 9, Apollo 4, TypeScript; Vitest und Playwright sind vorhanden. Keine Konva-, Fabric- oder Zustand-Abhängigkeit. Kein Grund, eine weitere Canvas-/State-/UI-Library einzuführen.

## State und Canvas-Struktur

Persistierte Daten liegen im Apollo-Cache; `SeatMapClientPage` besitzt kein lokales LayoutDocument. `selectedItems` ist zentral, enthält aber neben IDs kopierte Namen/Labels und Typen. Modus, Filter und Dialoge liegen ebenfalls in React State. Keine lokale Document-History.

`SeatMapCanvas` hält Scale, Translation, Pan-Flag, DragState, DragOffset, Debug-Flag und Mausposition in React State. Refs speichern Startpunkte für Pan. Keine Node Registry. Keine Stage/Layer/Group-Objekte einer Graphics-Library: äußere Box → transformierte World-Box → Section-Box → Table-Box → Seat-Button. Seats ohne Tisch liegen direkt unter Sections.

Kamera: CSS `translate(x,y) scale(scale)`, Ursprung `0 0`; Zoom zwischen 0.1 und 5. Pointerumrechnung: `(client - containerRect - translate) / scale`. Objektbewegung: `(client - startClient) / scale`. Pan verändert Translation; Zoom verändert Scale. Diese Kamera-Werte werden nicht direkt persistiert. Wheel-Zoom ist Ctrl/Cmd-gebunden und nicht pointerverankert. Fit läuft erneut bei Layoutänderungen.

Beim Mousedown startet ein Einzel-Drag, beim Mousemove wird DragOffset in React State geschrieben, beim Mouseup eine einzelne Mutation aufgerufen. Auch ein einfacher Klick kann so eine unveränderte Mutation auslösen. Mouseleave beendet den Drag. Auswahl erfolgt separat im Click-Handler. Ctrl/Cmd toggelt; Shift, Auswahlrechteck und Multi-Drag fehlen. Nur der Debug-Shortcut ist im Canvas registriert.

## Datenmodell und Koordinaten

`services/seat/prisma/schema.prisma`: PostgreSQL/Prisma, Sections, Tables und Seats als relationale Models. Kein SeatPlacement-Model; Sitzfachlichkeit und Geometry liegen gemeinsam in Seat.

| Model | Identität/Relationen | Geometry | Weitere Felder |
| --- | --- | --- | --- |
| Section | UUID, eventId; Name eindeutig pro Event | x/y, width/height, rotation, SectionShape, JSON meta | order, capacity |
| Table | UUID, eventId, sectionId; Name eindeutig pro Section | x/y, width/height, rotation, TableShape, meta | order, capacity |
| Seat | UUID, eventId, sectionId, nullable tableId | nullable x/y/width/height/radius/rotation; SeatShape; zIndex, hidden, locked, meta | status, number, label, note, seatType, guestId, invitationId |
| LayoutVersion | UUID, eventId, BigInt version; eindeutig eventId/version | JSON data, patch, inversePatch | label, createdAt |
| LayoutChangeLog | UUID, eventId, actorId UUID | JSON payload | enum type, createdAt |
| SeatAssignmentLog | UUID, eventId, seatId | keine Geometry | guestId/invitationId, action, data |

Prisma-Relationen löschen Kinder per Cascade. Eindeutigkeit von guestId und invitationId gilt pro Event. Presence, Invitations, Event-Zugriff, Event-Rollen und Settings sind lokale Projektionen. Das Schema besitzt kein tenantId an jedem Sitz; Event-Zugriff wird mit der authentifizierten Identität und Event-Access-Projektionen geprüft.

Der aktive GeometryEngine dokumentiert ein hierarchisches Mittelpunktmodell: Section absolut; Table relativ zum Section-Mittelpunkt; Seat relativ zum Table-Mittelpunkt, freie Seats relativ zur Section. Keine Kamera-Felder in Prisma. Rotation existiert, wird im bisherigen Renderer aber nur am Seat angewendet.

Shapes: Section = RECTANGLE/CIRCLE/POLYGON; Table = ROUND/RECTANGLE/OVAL/ROW; Seat = CIRCLE/SQUARE/RECTANGLE. TRIANGLE fehlt im bisherigen Contract. SeatStatus = AVAILABLE/RESERVED/ASSIGNED/BLOCKED; SOLD existiert nicht und darf nicht als geliefertes Backend-Feld behauptet werden.

## API und Datenfluss

```text
SeatMapClientPage → generierte TypedDocumentNodes → Apollo HTTP-Link
→ konfigurierter BACKEND_SERVER_URL → Federation Gateway
→ Subgraph seat (SEAT_URI, Default localhost:7409/graphql)
→ Nest Resolver → Read/Write Services → Prisma → PostgreSQL
```

Quellen: `src/lib/apollo/http-link.ts`, `src/lib/apollo/cache.ts`, `services/gateway/src/app.module.ts` (Subgraph `seat`), `services/gateway/src/config/env.ts`, `services/seat/src/config/graphql.ts`. HTTP verwendet Credentials/Cookies, optional Bearer und Request-/Event-Kontext. Kein eigener Seat-REST-Proxy in der Frontend-Route. Seat Service hat außerdem Health/Admin-HTTP-Endpunkte, die nicht der Editor-Speicherpfad sind.

`SeatMapView(eventId: ID!)`: `seatLayout` plus `seatPresencesByEvent`. Das Fragment `src/graphql/seat/fragments/seat-layout.fragment.graphql` enthält Sections und Tables mit Position, Dimensionen, Shape, Rotation, Meta; Seats mit ID, Position, Rotation, Nummer, Status, Meta, Parent-IDs und ColorGroup. Zusätzliche Seat-Queries und EventTree liefern Inhaber und Farbgruppen. Apollo normalisiert SectionPayload, TablePayload, SeatPayload nach ID; `seatLayout` ist eventbezogen und ersetzt Listen (`merge: false`).

| Operationen | Inputs/Ergebnis |
| --- | --- |
| seatLayout, layoutVersions, latestLayoutVersion, layoutChangeLog | eventId, optional limit; Sections/Versions/Logs |
| createSection, updateSection, deleteSection, renameSection, bulkRenameSections | Section-DTOs / ID; SectionPayload, Boolean oder RenamePayload |
| createTable, updateTable, deleteTable, renameTable, bulkRenameTables | Table-DTOs / ID; TablePayload, Boolean oder RenamePayload |
| createSeat, updateSeat, deleteSeat, assignSeat, unassignSeat | Seat-/Assignment-DTOs; SeatPayload/Boolean |
| moveSeat | id/x/y/optional rotation; SeatPayload |
| moveTable, moveSection | id/x/y; derzeit fälschlich als SeatPayload deklariert |
| duplicateTable | tableId, offsetX/Y; TablePayload |
| cloneSection | sectionId, offsetX/Y; SectionPayload |
| autoGenerateSeatMap | eventId, sectionName, seatCount, tableCount, TableShape, SectionShape, optional spacing; Boolean |
| autoGenerateLayout | eventId, SectionInput[] mit TableConfigInput[] und SeatConfigInput, adaptiveRadius; Boolean |
| saveLayoutVersion | eventId, version, label, data; LayoutVersionPayload; Service serialisiert DB und ignoriert input.data |
| undoLayout, redoLayout | eventId; Boolean |

DTOs liegen in den jeweiligen `models/inputs`, Outputs in `models/payloads`, Mappings in `models/mappers`. Schema ist Nest-code-first. Frontend-Codegen liest normalerweise Gateway-Introspection; `CODEGEN_OFFLINE=true` liest den vorhandenen Cache plus Overlay-Schemas. Generierte Dateien nicht manuell bearbeiten.

`SectionFieldsResolver.seats` filtert `tableId: null`: der öffentliche GraphQL-Renderer erhält keine absichtlichen Dubletten zwischen Section- und Table-Seats. `LayoutReadService` lädt zwar verschachtelte Relations vorab, Mapper werfen sie weg und Field Resolver laden sie erneut (N+1).

## Persistenz, History, Generatoren und Events

Create/Delete/Duplicate/Generate/Undo/Redo lösen einzelne Backend-Operationen aus, häufig mit anschließendem Refetch. Move sendet nur beim Mouseup, nicht pro Mousemove. UI-Catches sind leer. Kein expliziter Save, kein Dirty-State, keine atomare Multi-Operation.

History ist serverseitig: `LayoutWriteService.saveLayoutVersion` + `SnapshotSerializer`; Move schreibt ChangeLog und JSON-Patch, aber keine LayoutVersion. `undo`/`redo` suchen relativ zur höchsten Version ohne Cursor. Restore löscht das Layout und erzeugt Rows neu.

Aktiver Generator: `LayoutWriteService.autoGenerateSeatMap` → `autoGenerate` → `GeometryEngine.generate` → `writeGeometry`. `event.handler.ts` nutzt denselben Service zur automatischen Erstellung aus maxSeats. Zusätzliche reine Generator-Dateien in `layout/utils/shape` (Circle, Grid, Gala, U, Horseshoe, Scatter, Spiral, VIP), Collision/Spacing und `utils/layout` haben im aktuellen src keine Aufrufstellen außerhalb ihrer Definitionen/Registry. Nicht mit dem aktiven Pfad verwechseln.

Kafka-Handler: seat.create/delete, seat.addGuestId/removeGuestId, invitation.seatingInfoUpdated, event.created/updated, event.userAccessChanged/roleAssigned/roleRemoved/ownerChanged/deleted, event.milestoneRecorded. Sie pflegen Seats, Zuordnungen, Presence/Zugriff/Settings/Invitations und Analytics. Der Layout-Diff-Broadcast im LayoutWriteService ist auskommentiert; keine aktive Layout-Collaboration. Analytics besitzt eine Outbox/Publisher-Integration. Layoutarbeit muss Sitzidentitäten und Belegungen erhalten.

Migrationen: Initialschema; EventRoleProjection; SeatPresence/Table-Dimensionen; weitere Schemaanpassung; InvitationProjection; EventAccessProjection; Analytics-Outbox und Actor-ID-Migration. Bestehende Migrationen werden nicht nachträglich umgeschrieben.

## Implementierte Phasen 1–3 (2026-09-09)

Die vorausgehende Analyse beschreibt den Ausgangszustand. Der Frontend-Adapter normalisiert nun Section-, Table- und Seat-Mittelpunkte in ein ID-Record-World-Dokument. Editor und Viewer rendern flach. Die Route hält ausschließlich ausgewählte IDs; vorhandene Aktionen bleiben angebunden. Kamera-Fit wird nach initialem Laden nicht durch Bewegungen oder Refetch ausgelöst. Die Move-Persistenz sperrt parallele Dokumentänderungen und setzt lokale Geometrie bei Fehler zurück.

Rotation: Grad um den eigenen Mittelpunkt, positive Winkel im Bildschirmkoordinatensystem im Uhrzeigersinn. Parent-Rotation wird bei Bestandsdaten weder auf Kindpositionen noch auf Kindwinkel vererbt. Parent-Bewegung verschiebt Nachfahren einmal und erhält Backend-Offsets.

Die erweiterten Transform-, History-, Duplicate- und Atomic-Save-Vorschläge sind spätere Phasen. Wiederherstellbare Sicherung: `../../work-in-progress/seat-layout-later-phases-20260909`.
